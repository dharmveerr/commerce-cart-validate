## 4. Solution design

### 4.1 Building blocks

| Part | What it does | Where |
| --- | --- | --- |
| App definition | Declares settings, Admin menu and three webhooks | `app.commerce.config.ts` |
| Webhook action: item | Checks a line when an item is added or updated | `src/commerce-extensibility-1/actions/webhook/validate-cart-item/` |
| Webhook action: merge | Checks every line when a guest cart merges into a customer cart at login | `src/commerce-extensibility-1/actions/webhook/revalidate-quote-merge/` |
| Shared helpers | Read settings, compare quantity, optional correction | `src/commerce-extensibility-1/actions/lib/` |
| Native settings form | App Management business configuration (generated by the SDK) | `src/commerce-configuration-1/` |
| Custom Admin page | **Stores > Cart Item Validation** page plus GET/POST settings actions | `src/commerce-backend-ui-2/` |

### 4.2 Webhooks

| Commerce event | Action | When it runs |
| --- | --- | --- |
| `observer.sales_quote_add_item` | `validate-cart-item` | Item added to the cart |
| `observer.sales_quote_item_save_after` | `validate-cart-item` | Cart line saved, for example a quantity update |
| `observer.sales_quote_merge_after` | `revalidate-quote-merge` | Guest cart merged at login |

All three use `webhook_type: before`, `required: true`, a 5-second timeout and a 1-second soft timeout. If the action fails or times out, Commerce shows the fallback message: "Unable to update the cart right now. Please try again." The webhooks are subscribed automatically when the app is **installed** in App Management, not when it is deployed.

### 4.3 How a request flows

1. A shopper or Admin user changes a cart.
2. Commerce calls the matching webhook action.
3. The action reads the settings from global business configuration on **every call**, with no cache. A new limit therefore applies immediately (R-08).
4. The action compares the line quantity with `maxQuantity`.
5. The action returns `success` (allow) or `exception` (block, with a message).
6. If correction is on, an over-limit line found on save or merge is set back to the maximum through the Commerce Cart REST API.

### 4.4 Settings

| Setting | Default | Meaning |
| --- | --- | --- |
| `enabled` | `true` | Switches validation on or off |
| `maxQuantity` | `10` | Maximum quantity per cart line (a positive whole number) |
| `enableCompensatingCorrection` | `true` | Sets an over-limit line back to the maximum on save or merge |

You can edit them in two places that share the same stored values: the App Management form and **Stores > Cart Item Validation**.

### 4.5 Decision rules (current code)

| Situation | Result |
| --- | --- |
| Validation disabled | Allow |
| Quantity is `0` (line removed) | Allow |
| Quantity ≤ maximum | Allow |
| Quantity > maximum | **Block** with `You have reached the maximum amount of items.` |
| Item missing from the payload | Allow, and log an error (`invalid_payload`) |
| Quantity not a number | Allow, and log an error (`invalid_quantity`) |
| Settings cannot be read or are invalid | Allow, and log an error (`fail_open`) |
| Merge: any line over the maximum | Block with the same message. Bad lines are logged and skipped. |

Only a business-rule violation blocks a cart. Technical problems are allowed and logged, so a payload mismatch cannot block shoppers.

### 4.6 Security

- Webhook and settings actions require Adobe authentication (`require-adobe-auth`).
- The settings actions also check the Admin menu permission on the server.
- Credentials stay in the local `.env` and `.aio` files, which are not committed.

### 4.7 Key design choices

| Choice | Reason |
| --- | --- |
| Three webhooks (add, save, merge) | Cover every way a quantity can change |
| Limit per cart line | Follows CDA Blueprint v7. The client text points to a cart total (Q-2), which will be built on a separate branch. |
| Optional correction | `_after` events may not undo a save, so the app can fix the line itself |
| Two settings screens | Kept until the client decides which one to keep |
