# Cart Item Validation deployment and validation runbook

## Developer Console / deployment checklist

1. Choose an **ACCS sandbox** workspace in Adobe Developer Console. In this project's **Integrations** page configure its organization, project, workspace and Runtime credentials `AIO_runtime_namespace` and `AIO_runtime_auth` using the authorized secret store; do not put the values in source, chat, or the committed config. The previous deploy attempt stopped **before starting** because those two keys were absent.
2. Subscribe the workspace to the SDK-required **AdobeIOManagementAPISDK** (I/O Management API) and ACCS **ACCS-REST-API**; connect the relevant ACCS project with App Management. Ensure IMS credentials from the workspace are provisioned for App Management association and that the IMS technical account can read and edit cart items in each environment. Confirm actual permissions for dev/stage/production; role names vary. If workspace login or subscription is incomplete, finish those steps in Developer Console before retrying.
3. After providing credentials, regenerate `npx aio-commerce-lib-app generate all`, run `npm install`, `npm run typecheck`, `npm run test`, `aio app build`; generated `web-src/src/config.json` contains `undefined.adobeio-static.net` when the workspace context is absent, so **verify its regenerated action URLs contain the correct namespace** before opening the Admin page. Do not hardcode or commit generated URLs. Configure the app's Runtime/IMS variables through the supported Integrations flow and check that no bound input is missing.
4. On explicit approval deploy with `aio app deploy`. **Deploy does not install** an App Management app on ACCS: associate and install it in Commerce Admin, verify the three webhook registrations, native Business Config and custom Stores menu entry, and grant the menu ACL to intended Admin roles. `require-adobe-auth` restricts action access by IMS; both custom settings actions additionally check the menu ACL server-side. Test allowed and denied roles directly, since a hidden menu alone is not an authorization test.
5. Candidate observer names/payload shapes and the ACCS timeout/observer ordering remain unverified. Inspect the Admin webhook test tool and **System > Webhook Logs** to confirm dispatch. An after-named observer with `webhook_type: before` might not roll back. Do not call this app operational or list it on Marketplace until `verified-contracts.md` is filled with live evidence. Test installation/upgrade on at least two ACCS projects; no fixed backend URL, org or store code is assumed.

## Smoke tests

1. In native App Management settings set Enabled=true, Max Quantity=10, Enable Compensating Correction=true. In the custom Stores menu page load the same three values, save Max Quantity=5, refresh both UIs, and confirm storefront rejection tracks 5 immediately. Try invalid 0, fractional and enormous maximum values: custom UI/action must reject them. Native text field has no numeric type; invalid native values cause the runtime reader to fail open (inspect structured error logs). Resolve invalid values before release.
2. In the Commerce Admin webhook test tool submit item payloads at boundary, above boundary, invalid/missing qty and qty=0 removal; verify returned success/exception operation and handler/source/decision logs. Test storefront guest add, customer add, cart qty update and remove, then independently query the cart after each mutation. Test simple, configurable and bundle parent **and** child lines. Live dispatch per row is an open assumption.
3. Merge a guest cart with a customer cart whose combined per-line quantity exceeds the limit; inspect the first offending SKU message, UX behavior, and final cart quantity independently. Sign off customer-facing merge-block message. Re-run with correction off to isolate rollback. Re-run with correction on to verify <=maxQuantity postcondition. Use separate disposable carts for each attempt.
4. In Commerce Admin's **Create New Order** flow try above-limit and valid quantities. Confirm webhook dispatch and end state: do not assume the Admin route shares the storefront trigger. Test changes concurrently with compensation; the read-before-write guard must skip stale quantities. Inspect `CRITICAL` log on exhausted retry and verify manual recovery.
5. Run `npm run test:sandbox` with the environment variables, cart preparation and two explicit correction modes listed in `verified-contracts.md`. The command intentionally fails if variables are missing. Verify latency against actual ACCS timeout and repeat after upgrade and on a second project.

## Operations and limitations

- Kill switch: set Enabled=false in **native Business Config** (independent of custom UI availability) and verify a new cart request bypasses the rule. Disable `enableCompensatingCorrection` alone to keep blocking but stop REST writes. Never turn off a production safeguard without change approval.
- On `CRITICAL` correction logs, check the identified quote/item in Commerce Admin or with an authorized cart query, manually reduce/remove excess lines, then verify final state. Investigate technical account ACL, expired association and transient HTTP errors. Never log tokens or cart PII.
- Business Config fetch failure **fails open** for cart hooks; invalid native Max Quantity also fails open. Set operational alerts on `phase: configuration, decision: fail_open` and `phase: compensation, decision: CRITICAL`. Admin settings actions fail closed instead.
- Bulk/CSV imports and other quote modifications not covered by the three candidate observers are outside this webhook guarantee. Admin UI SDK only manages settings, not storefront cart validation. Multi-store rules, aggregate SKU quantity and automatic remediation across historical carts are outside current scope.
- Marketplace readiness gate: after validation compare native Business Config to the custom UI, then decide whether the bespoke page justifies ongoing cross-project maintenance; **keep both for now**.
